---- 二、建之前要处理的 3 件事 ----
================================================================

问题1 | B3 实体标注是死代码【必须建前定，建完改要重建】
   位置: scripts/build_lightrag_index.py:55-70 与 :76-81
   现状: 标注算出来了（打印 101 的计数），但 :76-81 只收集 text / id / file_path，
         entities_a / entities_b 从未传给 LightRAG
   后果: 上一轮说的"8.7% 的块有标注"实际是 0%；
         没有标注时 LightRAG 自由抽取，实测会产出
         PubMed->安德森癌症中心、吸烟->美国癌症协会 这类机构垃圾节点
   为什么必须现在定: 它改变送进 LightRAG 的文本内容，建完再改要重建
   两个选择:
     (a) 拼一个短前缀进文本，例如
         "[exposure: current_smoking | outcome: cataract_any]\n" + 原文
         对 101 个规则块有效；其余 953 块可做关键词匹配补，或放弃
     (b) 删掉这段代码，接受自由抽取
   建议: 选 (a)，至少对那 101 个规则块做 —— 它们是规则证据，最需要对齐
         注意: 其余 953 块即使不标注也不影响公平性，但要接受 KG 里混入泛实体

问题2 | 没有续传逻辑【建议建前做，建完也能加】
   位置: scripts/build_lightrag_index.py:102
   现状: 每次都把全部 1054 块重新 enqueue
   后果: (a) 每次重跑往 doc_status 写 1054 条 dup-* FAILED 记录
         (b) 没有"跳过已完成"的判定
         (c) 中途被 kill 留下的 processing 残留不会清理
   说明: LightRAG 幂等，所以不会重复花 LLM 钱；但 1054 块要跑 1-2 小时，
         中途断了你会希望直接续上而不是重跑全部
   最小实现（插在 insert 之前）:
     读 working_dir/kv_store_doc_status.json
       doc_id 以 dup- 开头             -> 忽略（关键：否则会被当失败反复重试）
       processed 且 content_hash 一致   -> 跳过
       processing / parsing / analyzing -> adelete_by_doc_id 后重插
       其余                             -> 插入

问题3 | os._exit(0) 没有 flush，管道输出会丢【一行修复】
   位置: scripts/build_lightrag_index.py:119
   现状: os._exit() 跳过缓冲区刷新；当输出重定向到文件或管道时（非 tty），
         stdout 是块缓冲的
   后果: 最后那几行（Done in Xs / Stats / B5 警告）可能全丢 ——
         一个跑了两小时的构建看起来像什么都没输出
   修法: os._exit(0) 之前加 sys.stdout.flush()
